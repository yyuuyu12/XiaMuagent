# 第一部分：后端 · 生成质量与学习闭环（任务 1-5）

## 任务 1：生成质量修复（模型、温度、截断检测）

**目标（说人话）**
现在你遇到的"AI 回了一堆话但稿子没变""3 分钟的稿子写到一半没了""同一个大纲两次生成一次能用一次不能用"，根子都在这一个任务里。改完后：长稿不再半路断掉；断了也会明确告诉用户而不是装没事；两次生成的质量差距明显缩小。

**现状问题**
- `lib/callAI.js` 里有个全局输出上限 `max_tokens_cap`（注释提到中转站限 1200 token ≈ 850 个汉字）。3 分钟剧本的完整输出（450 字正文 + 画面标注 + 摘要 + 格式标签）会超过这个上限，**被静默砍断**。
- 砍断后输出缺少结尾的 `【/新剧本】` 标签 → `routes/original.js` 的 `extractStageDoc()` 正则匹配不到 → 系统认为"这次没有产出文档" → 稿子不更新，用户只看到一段没头没尾的回复。这就是"稿子没变"的直接原因。
- `generateStageReply()` 里 `temperature: 0.85`，相当于让 AI 每次都"放飞"，质量随机波动大。
- 默认模型配置全是便宜档（gpt-3.5-turbo / claude-haiku / glm-4-flash / qwen-turbo），写不出优质文案是正常的——不是流程问题，是模型本身的上限。

**改动点（给 Claude Code）**

1.1 `lib/callAI.js`：
- `callAI(prompt, opts)` 新增两个可选参数：`opts.model`（覆盖配置中的默认模型名）、`opts.bypassCap`（true 时忽略 `max_tokens_cap` 限制）。
- 五个 provider 分支（openai/qwen/claude/zhipu/deepseek）统一支持这两个参数。

1.2 `system_config` 新增两个配置项（initDb.js 预置空值，admin.html 增加对应输入框）：
- `ai_model_creation`：创作类任务（方向/粗纲/细纲/剧本生成）专用模型名，留空则用默认模型。目的：聊天、提取这类便宜任务继续用便宜模型，**只给写稿环节配一线模型**（建议 deepseek-chat 即 V3，或 Claude Sonnet 档），控制成本。
- `critic_enabled`：'1' / '0'，任务 5 的质检开关。

1.3 `routes/original.js` → `generateStageReply()`：
- `temperature` 从 0.85 改为 **0.65**。
- callAI 调用加 `bypassCap: true`；若 system_config 配置了 `ai_model_creation` 则传 `model`。
- **截断检测**：AI 返回后检查——若包含开标签 `【${tag}】` 但没有闭标签 `【/${tag}】`，判定为截断。处理方式：
  - 取开标签之后的全部内容作为 newDoc，`hasDocUpdate = 1`（残稿也比不更新强）；
  - 在 aiSummary 末尾追加提示：「（本次输出可能不完整，建议点重新生成，或在设置里缩短目标时长）」；
  - `console.warn('[Truncated]', stage, project.id)` 留日志，便于统计截断频率。

**产品验收（你自己点）**
1. 新建项目，时长选 **3 分钟**，走到剧本阶段，连续点 10 次"重新生成"（或发 10 次修改指令）。10 次中**每一次**右侧文档都要有变化——出现哪怕一次"AI 回了话但文档纹丝不动"就是不通过。
2. 同一份细纲生成 3 版剧本，肉眼对比：3 版都应该是完整的（有开头有结尾有引导），字数大致相当。
3. 在管理后台把 `ai_model_creation` 配成 deepseek-chat，再生成一版，和默认模型的产出对比质量（这一步同时验证了配置生效）。

**技术验收（Claude Code 自测）**
- 模拟 AI 返回只有开标签没有闭标签的字符串，确认 newDoc 取到残稿、aiSummary 带提示、日志有 `[Truncated]`。
- 确认 `bypassCap: true` 时请求 body 中 max_tokens = 4000 而非被夹到 1200。

## 任务 2：把"项目级学习"从假功能变成真功能

**目标（说人话）**
现在学习中心有个选项叫"仅用于本项目"，用户选了它，系统提示"规律已记录，本项目对话时会参考"——**但后端实际上什么都没存，之后也完全不会参考**。这是在骗用户。改完后：选"仅本项目"学到的规律会真实存进该项目，之后这个项目里每次生成都会带上这些规律。

**现状问题**
`routes/original.js` → `POST /learning/write`：开头就是 `if (scope !== 'global') return res.json({ code:200, msg:'规律已记录...' })`，直接返回成功，零存储、零后续动作。

**改动点（给 Claude Code）**

2.1 `learning/write` 中 scope 为 project 时：
- 校验 projectId 存在且属于当前用户，否则返回 400。
- 读取该项目的 `meta` JSON 列，在 `meta.projectRules`（字符串数组，不存在则初始化）末尾追加本次 insights 的 text；按"去空格后的文本"去重；上限 20 条，超出移除最旧的。
- 写回 `cw_original_projects.meta`。

2.2 `buildStagePrompt()`：
- 解析 `project.meta.projectRules`，非空时在 Skill 区块之后插入：
  ```
  ## 本项目专属规律（仅本项目生效，与全局 Skill 冲突时以本区块为准）
  - {逐条列出}
  ```

**产品验收（你自己点）**
1. 进入某个项目 → 学习中心 → 选"仅用于本项目" → 拆解一条链接 → 勾选 2 条规律写入。
2. 回到该项目对话，发"按学到的规律重写开头"——产出应明显体现刚学的规律（比如学的是"开头用数字"，新稿开头就该有数字）。
3. **换一个项目**发同样指令——不应体现这些规律（证明确实只在本项目生效）。

**技术验收**：写入后 `GET /projects/:id` 返回的 meta.projectRules 包含这 2 条；后端日志打印的 prompt 含"本项目专属规律"区块。

## 任务 3：编辑 diff 学习 —— 用户改稿，AI 自动学

**目标（说人话）**
这是"Skill 自我学习"的核心。用户亲手把 AI 的稿子改成自己满意的样子，这个"改动本身"就是最真实的偏好表达——比打字告诉 AI"要口语化一点"准确十倍。改完后：用户定稿时，系统自动对比 AI 原稿和用户终稿，提炼出"原来你喜欢这样写"的规则，下次进原创工坊时弹出来问你"要不要让我以后都这么写"。**这就是用户能感知到的"它在学我"。**

**现状问题**
`PATCH /projects/:id` 支持保存用户手动编辑后的 doc，但保存就是直接覆盖，AI 版和用户版的差异没有被任何逻辑利用，最有价值的学习信号被白白丢掉。

**改动点（给 Claude Code）**

3.1 记录 AI 基线：
- `chat` 接口与 `stage/advance` 中，凡 `hasDocUpdate=1` 写 doc 的位置，同步在 artifacts 里记 `_aiBaseline = { stage, doc: newDoc, at: Date.now() }`。
- artifacts 中 `_` 开头的键约定为内部数据。**同步检查 index.html 中所有读取 artifacts 的渲染位置（阶段快照展示等），确保跳过 `_` 开头的键**，否则前端会把内部数据当阶段产出渲染出来。

3.2 定稿触发提炼，新函数 `extractEditDiffRules(project, userId)`：
- 触发点两处：`PATCH /projects/:id` 收到 `status='final'` 时；`stage/advance` 的 done 分支（最后阶段确认）。两处都**异步调用、不阻塞响应**，失败仅 console.warn。
- 函数内部逻辑：
  - 取 `artifacts._aiBaseline.doc`（AI 最后一版）与当前 `project.doc`（用户终版）。任一为空、两者去空格后相同、或 baseline 的 stage 不是 script → 直接 return。
  - 差异门槛：字符级差异量 / 终版长度 < 8% 时 return（只改了错别字不值得学习）。
  - 调 callAI（temperature 0.3，maxTokens 300），prompt 原文：

    ```
    你是写作风格分析师。下面是 AI 生成的口播剧本初稿和用户亲手修改后的定稿。
    【AI 初稿】{baseline 前 800 字}
    【用户定稿】{终版前 800 字}
    任务：对比两版差异，提炼用户的写作偏好，输出 1-3 条可复用的写作规则。
    要求：
    - 每条说清楚「什么情况下，怎么写」，要具体到写法，不要空洞结论
    - 每条 20-50 字，一行一条，以 - 开头
    - 差异若只是错别字或事实修正，输出 SKIP
    只输出规则行或 SKIP。
    ```
  - 每条解析出的规则调 `addPendingRule(userId, text, 'diff', '项目#{id}定稿对比')` 进入待确认池（函数定义见任务 4，编码时可在本任务先建）。

**产品验收（你自己点）**
1. 建项目走到剧本定稿前 → 手动大改 doc（比如把所有"你是不是也…"开头删掉、改成直接报数字）并保存 → 点定稿。
2. 退出回到原创工坊首页 → 应出现"我学到了 N 条新写法"的卡片（任务 4 的 UI）→ 点开看内容，提炼出的规则应与你刚才的改动方向一致（比如"开头不用反问句，直接抛数字"）。
3. 反例：另建一个项目，定稿前只改两个错别字 → 定稿后**不应**产生新的学习卡片。

**技术验收**：上述操作后 `cw_skills.rules` 的"待确认"分组出现 pending 条目，sourceType='diff'；轻微改动场景不产生条目。

## 任务 4：学习提议制 + Skill 治理 —— 学到的东西看得见、管得住

**目标（说人话）**
系统其实早就有一个"自动学习"：你在对话里说"好多了""太 AI 味了"，它会偷偷提炼一条规则塞进 Skill 文档末尾。问题是它是**静默的**——你不知道它学了什么、学得对不对、也删不掉，时间长了 Skill 被低质量规则塞满，反而把生成质量拖下水。这也是你体感"它不会学习"的原因之一：它学了但你看不见。
改完后：所有自动学到的规则（对话反馈学的 + 任务 3 改稿学的）统一进"待确认"列表，首页弹卡片让你逐条"采纳/忽略"，**只有你采纳的才会真正影响生成**。另加一个"一键整理"按钮清理历史遗留的杂乱规则。

**现状问题**
- `chat` 接口中的 auto-learn：正则匹配短反馈 → 提炼规则 → 直接 append 进 free_text 的「## 自动学习」区块。无确认、无去重、无上限、用户无感知。
- 历史已积累的「## 自动学习」条目可能互相重复矛盾，没有清理手段。

**改动点（给 Claude Code）**

4.1 统一入口 `addPendingRule(userId, text, sourceType, source)`：
- 写入 `cw_skills.rules` 的 `'待确认'` 分组，条目结构 `{ text, source, sourceType, uses: 0, pending: true, at: 时间戳 }`。
- 去重：与**全部分组**现有条目按去空格文本比对，重复则跳过。
- "待确认"分组上限 10 条，满则移除最旧。
- **关键约束**：`formatRulesForPrompt()` 必须跳过 `pending: true` 的条目及整个"待确认"分组——没被用户采纳的规则绝不能进入生成 prompt。

4.2 chat 中现有 auto-learn 段：删除直接改 free_text 的写入逻辑，改为调 `addPendingRule(..., 'feedback', '对话反馈')`。正则触发条件本身保留不动。

4.3 新接口三个：
- `GET /original/skill/pending` → 待确认列表（带索引）。
- `POST /original/skill/pending/:idx/confirm` → 该条 pending 置 false 并移入 `'自动学习'` 分组；Skill 版本号 minor +1（复用 PATCH 项目里现成的版本号自增写法）。
- `POST /original/skill/pending/:idx/dismiss` → 删除该条。

4.4 H5 前端（index.html）：
- `enterOriginal()` 拉 skill 后若有 pending 规则，在 `tOriginalHome()` 顶部渲染卡片：「✨ 我从你的反馈/修改中学到了 N 条新写法」→ 点开逐条展示，每条带「采纳 / 忽略」，分别调上面的接口；交互样式复用现有 `syncOriginalRule` 同步卡片的风格。
- 卡片需标注来源（"来自对话反馈" / "来自你的定稿修改"），让用户知道它是从哪学的。

4.5 freeText 治理：
- 新接口 `POST /original/skill/compact`：把 free_text 中所有「## 自动学习」区块的条目交给模型合并去重精炼（temperature 0.3），重写回单个区块；执行前把旧 free_text 推入 `free_text_history`（列已存在，遵循现有历史结构，保证可还原）。
- H5「我的 Skill」页加「整理自动学习记录」按钮调用，成功后 toast 显示"已合并 X 条 → Y 条"。

**产品验收（你自己点）**
1. 在项目对话里发"这版好多了，没那么 AI 味了"→ Skill 文档（我的 Skill 页）**不应**出现新内容 → 回原创工坊首页 → 出现学习卡片 → 点"采纳"→ 再看 Skill，规则出现在"自动学习"分组。
2. 同样操作但点"忽略"→ 规则消失，Skill 无变化。
3. 待确认状态下（未采纳前）让 AI 生成一版稿子——稿子不应体现该规则（证明 pending 不进 prompt）。
4. 「我的 Skill」页点"整理自动学习记录"→ 条目变少且不丢关键信息 → 历史记录里能还原整理前的版本。

**技术验收**：pending 条目在日志打印的 prompt 中不出现；待确认分组到 10 条后第 11 条挤掉最旧；compact 前的 free_text 进入 history。

## 任务 5：规则使用计数 + 剧本质检（critic 自检）

**目标（说人话）**
两件事。第一，现在 Skill 里每条规则都有个"使用次数"字段，但从来没人记数——接上之后你能看到哪些规则真的在被用、哪些是死规则，为以后淘汰和调权打基础。第二，现在 AI 写完稿直接交，没有自查；改完后它会先按你的验收标准（字数、禁区词、开头钩子、口语化）自己检查一遍，不合格自动重写一轮再给你——**相当于给 AI 配了个质检员**，这是把"内容不够优质"往上拉的流程保障。

**现状问题**
- `cw_skills.rules` 条目的 `uses` 字段全代码无任何累加逻辑。
- `cw_skills.check_prompt` 列已建但无消费方。生成单轮直出。

**改动点（给 Claude Code）**

5.1 规则编号与使用回执：
- `formatRulesForPrompt()` 给每条结构化规则生成稳定编号 `[R1]、[R2]…`（按分组顺序展开），输出形如 `- [R3] 开场必须是动作或数字`。freeText 部分不编号。
- 仅 script 阶段 prompt 末尾追加：「输出最后单起一行写 USED:R编号列表（本次实际遵循的规则，没有则写 USED:无）。此行不属于剧本内容。」
- `generateStageReply()` 解析 USED 行并从 aiSummary / newDoc 中剥离（用户不应看到这行），按编号给对应规则 `uses` +1 写回。解析失败静默跳过。
- 「我的 Skill」结构化规则展示处（如有）显示 uses 次数；没有现成展示位则本期只入库不展示。

5.2 critic 质检（仅 script 阶段，`critic_enabled='1'` 时生效）：
- 位置：`generateStageReply()` 解析出 newDoc 且 hasDocUpdate=1 之后。
- 评审调用（temperature 0.2，maxTokens 500，bypassCap），prompt 原文：

  ```
  你是短视频口播剧本的质检员。按以下标准审查剧本，只输出 JSON。
  【剧本】{newDoc}
  【硬性标准】
  1. 字数符合目标：{durationLabel}（允许 ±20%）
  2. 不出现以下禁区内容：{skill.forbidden 列表，为空写"无"}
  3. 开场前两句必须有钩子（数字/反差/悬念/动作之一），不得自我介绍
  4. 口语化：不出现"首先/其次/综上所述"等书面框架词
  ```

## 任务 9：本地算力离线时的友好降级

**目标（说人话）**

**现状基础**
